# 形状问卷（pattern-spec v0.1，实验稿）

> 状态：**实验**。还没有接进 zoom / flow 规程，也没有机械提取器。
> 实测依据见 `eval/pattern-coverage.md`（7 类代码、29 个模块的手工作答）。

目的：让"这段代码画成什么"不再是每次由模型自由判断，而是**对固定的几个问题给出封闭选项的答案**，
答案机械映射到画法。不穷举 pattern（列不完），穷举维度（每个维度的选项是封闭分区，任何代码必然落在某一格）。
具名 pattern（生产者-消费者、状态机、LRU……）是几个维度答案的组合，不需要预先列出。

## 0. 分析单位：两种，不是"模块"

问卷不对"模块"作答。一个模块里常常有几条各自循环的执行流和几块各自的状态
（Raft 的 ConsensusModule 里有 4 条 goroutine、1 个状态变量、1 条日志），按模块答会答成一锅粥。

| 单位 | 是什么 | 怎么找（机械） | 回答哪些题 |
|---|---|---|---|
| **数据体** | 一块跨调用存活的状态：全局变量、结构体/对象的字段、组件 state、表 | 类型声明、字段、`useState`、模块级赋值 | D1 形状 · D2 模式 · 游标 · 不变量 |
| **执行流** | 一条从入口跑到底的控制流：线程/协程入口、循环体、请求处理函数、回调、被导出的函数 | spawn 点（`go`、`Thread(`、`create_task`）、注册点（装饰器、`on*=`、路由表）、导出符号 | F1 执行者 · F2 交接 · F3 重复 · F4 选择 · 输入/输出形状 |

两者之间的边 = **访问**：执行流读 / 写 / 阻塞在哪个数据体上。这三样（数据体、执行流、访问边）就是画布的全部骨架，
对应场景层已有的 `queue/store/log/grid`、`thread/ext`、`wires`。

## 1. 数据体的题

### D1 形状（实现形状，封闭 7 选 1，可嵌套）

`标量` · `序列`（数组 / 链表 / 队列 / 栈 / 环）· `映射` · `树` · `图` · `网格`（矩阵 / 张量 / 位图）· `记录`（几个不同字段的积，逐字段再答）

- 封闭的理由：数据类型的构造方式只有积、和、序列、映射、递归引用这几种。
- **答实现形状，另填一个 `role`（逻辑角色）**。两者经常不同：chibicc 的 hashmap 实现是数组 + 线性探测，角色是映射；
  xv6 的 bcache 实现是双向链表，角色是按最近使用排序的缓存；sortedcontainers 的 `_index` 实现是数组，角色是树。
  画实现形状（读者要对得上代码），标题写角色。
- 嵌套写成 `序列<序列>`、`映射<标量, 序列>`，最多两层；更深的拆成几个数据体。
- 机械信号：类型声明（C / Go / TS / Rust 可直接读出）；自引用指针字段 `next/prev/left/right/children/parent`；
  下标算术 `% cap`（环）、`(i-1)>>1` / `2*i+1`（数组里的树）。动态语言只能从初始化字面量和用法推，需要模型。

### D2 模式变量（封闭 3 选 1）

`无` · `显式`（一个 enum / 布尔 / 字符串字段决定"现在是哪种行为"）· `隐式`（几个 flag 或计数器的组合决定）

- 显式时**转换表可以机械提取**：对这个字段的每一处赋值 = 一条转换的终点；包住它的最近一层 `if state == X` = 起点；
  所在函数 = 触发者。xv6 的 `p->state` 有 11 处赋值散在 11 个函数里，全部能这样抓出来。
- 隐式的要模型判断，并且必须写出"哪几个变量的哪种组合 = 哪个模式"（xv6 `log.committing` + `log.outstanding`）。
- 反例：只在初始化时写一次的配置开关不是模式变量。

### 游标（0 到多个）

指向这个数据体内部某个位置的变量：下标、指针、迭代器、offset、水位线、当前节点。写 `[名字, 指向谁, 谁移动它]`。
机械信号：出现在下标 / 切片位置的整型变量（`log[lastApplied+1 : commitIndex+1]`、`data[nwrite++ % PIPESIZE]`）；
`p = p->next` 形式的自更新。Raft 的 `nextIndex[peer]` 这种"游标的映射"照常写，形状是 `映射<peer, 游标>`。

### 不变量（必填一句，模型写）

这个数据体始终成立的关系，用它自己的字段写：`nread ≤ nwrite ≤ nread + PIPESIZE`；`每个子列表长度 ≤ 2 × load`。
这是唯一不能机械化的槽位，也是图上最值钱的一行。必须附 `[文件, 行]`：代码里检查或维持这个关系的那一行。

## 2. 执行流的题

### F1 执行者（封闭 4 选 1）

`被调用`（没有自己的执行流，谁调它就在谁的流里）· `自有`（一条线程 / 协程 / 主循环）· `每任务一条`（每个请求 / 每个 peer 派生一条）· `框架代持`（入口由框架或运行时调用，调用点不在本仓库）

- `框架代持` 是 v0 没有的选项。Django 视图、React 组件、pytest 用例、Spring bean 都是它：仓库里看不到谁在什么时候调用。
  这时**不要猜**，按 §4 处理。
- 机械信号：是不是某个 spawn 点的目标；是不是注册点的目标；都不是且被本仓库别处调用 = 被调用。

### F2 交接（这条流怎样把控制权或数据交给别的流，可多选，封闭 6 种）

`调用-返回` · `消息`（入队 / channel / 发 RPC）· `等待-唤醒`（锁、条件变量、sleep/wakeup、semaphore、join）· `让出-恢复`（await / yield / 上下文切换）· `注册-回调`（future、事件、定时器、信号、props 回调）· `派生`（起一条新流，不等它）

- `等待-唤醒` 是 v0 漏的：xv6 的 pipe / log / bio 全靠它，而它既不是消息也不是回调。
- 封闭的理由：交接 = {同步, 异步} × {数据走, 控制走} × {谁负责恢复}，上面六种是这个积里实际存在的格子。
- 机械信号是**分生态的词表**：语言级的（Go `<-` / `select` / `go`，Python `await` / `yield` / 装饰器，JS `on*=` / `.then`）可以直接认；
  项目自定义的原语（xv6 的 `sleep()` / `wakeup()` / `swtch()`）需要先由模型或人认一次，写进本仓库的词表，之后机械。

### F3 重复（封闭 5 选 1，嵌套时由外到内各答一次）

`无` · `逐元素` · `直到条件`（重试、二分、不动点、扫到结尾）· `永远`（主循环，靠 break / 关闭退出）· `递归`

- 机械信号：AST 的循环节点类型和条件（`for x in`、`while cond`、`for(;;)` / `while True`）；递归 = 调用图上有环（含互递归：`expr → assign → … → primary → expr`）。
- 29 个模块里这一题 19 个非"无"的答案**全部**可由语法决定。

### F4 选择（封闭 3 选 1）

`无` · `条件分支`（按数据的值走不同路；守卫 + 提前返回也算）· `分派`（按一个种类标签选处理者：`switch(kind)`、函数指针表、映射查表、虚函数 / 多态）

- v0 完全漏了这一维。结构化程序定理的三件套是顺序、选择、重复，v0 只问了重复。
  xv6 `syscalls[num]()`、chibicc `switch (node->kind)`、React `FILTER_MAP[filter]` 的主要结构都是分派。
- 机械信号：`switch` / `match`；以变量为下标调用（`table[k](…)`）；按类型的方法查找。

### 输入 / 输出形状

这条流吃进什么形状、吐出什么形状（用 D1 的选项）。对**不持有状态的变换型代码**这是主要信息：
编译器每一趟（字符序列 → token 序列 → 树 → 文本），模型前向（网格 `(B,T)` → `(B,T,C)` → `(B,T,V)`）。
v0 只问"持有什么"，对这类代码五题全答"无"，等于没问。

## 3. 答案 → 画法（固定映射）

| 答案 | 画成 | 现有渲染器 |
|---|---|---|
| D1 序列 / 映射 / 树 / 网格 / 标量 | 对应的数据结构图形 | `fields.shape`、场景 `queue / store / grid`（树、图要补） |
| D2 显式 | 状态图，边 = 机械提取的转换表 | `anatomy: statemachine` |
| 游标 | 数据图形上的带名指针，随故事移动 | 场景 `log.markers`（要推广到序列 / 树） |
| 不变量 | 数据图形下方固定一行 | 要补 |
| F1 自有 / 每任务一条 | 泳道 / 执行者实体；每任务一条画成一叠 | 场景 `thread`、`group` |
| F2 各种交接 | 连线类型 | 场景 wire `call / queue / cb / ipc`（等待-唤醒、让出-恢复要补） |
| F3 永远 | 环 | `anatomy: loop` |
| F3 逐元素 / 直到条件 | 游标扫过数据图形 | 靠游标 |
| F3 递归 | 调用栈 + 树上的当前节点 | 要补 |
| F4 分派 | 上方一个判据、下方并列分支 | `anatomy: dispatch` |
| F4 条件分支，其余全"无" | 退化为流程图 | `anatomy: flow` |
| 输入 ≠ 输出形状 | 左右两个数据图形，中间是变换 | `anatomy: pipeline` |

具名 pattern 不进这张表。"两条自有执行流 + 一个序列 + 等待-唤醒" 自然画成生产者-消费者，不需要有人认出它叫什么。

## 4. 问卷管不到的（明说，不硬套）

1. **框架代持的结构**（F1 = 框架代持）：请求从进来到视图函数之间的认证、权限、序列化、信号，全在框架里。
   仓库里只有声明式的配置。出路只有两条：按框架写一次**生命周期包**（Django / DRF、React、Spring…… 各一份固定骨架，
   仓库代码往槽位里填），或者真跑一遍拿 trace。在那之前，这类模块只能画成"框架调用我 → 我的流程图"。
2. **领域想法**：注意力在算什么、宏展开为什么不会无限递归（hideset）、DP 递推为什么对。
   问卷能给出机制（形状怎么变、循环怎么走），给不出"为什么这样就对"。这部分仍是模型写的讲解。
3. **非执行性代码**：配置、schema、类型定义。只有 D1（通常是图），没有执行流。

## 5. 作答格式（草案）

```jsonc
{"data": [
  {"id": "pipe", "decl": ["kernel/pipe.c", 13, "struct pipe"],
   "shape": "序列", "role": "有界字节队列", "impl": "环（下标 % PIPESIZE）",
   "mode": "无",
   "cursors": [["nread", "data", "piperead"], ["nwrite", "data", "pipewrite"]],
   "invariant": ["nread ≤ nwrite ≤ nread + PIPESIZE", ["kernel/pipe.c", 88]]}],
 "flows": [
  {"id": "pipewrite", "entry": ["kernel/pipe.c", 77, "pipewrite"],
   "executor": "被调用", "handoff": ["等待-唤醒"], "repeat": ["直到条件"], "select": "条件分支",
   "in": "序列", "out": "标量",
   "access": [["pipe", "写"], ["pipe", "阻塞：满"]],
   "evidence": {"handoff": [["kernel/pipe.c", 92, "sleep"], ["kernel/pipe.c", 105, "wakeup"]]}}]}
```

每个非"无"的答案都要有 `[文件, 行, 符号]`，`check_refs.py` 现有的核对方式可以直接用。
