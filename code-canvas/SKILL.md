Produces a self-contained HTML canvas of function-level code cards laid out spatially, with typed wires (call vs data flow) anchored to specific lines, line-attached intent notes, teal background notes, colored storyline regions, and a step-by-step guided camera. Use when the user wants to understand a codebase, walk through code, or review changes visually — triggers include "walk me through", "explain this code", "how does X work", "make a canvas/walkthrough of", or dissatisfaction with reading long diffs top-to-bottom.

# code-canvas skill (v0.2 · agent 版)

代码是源码，图是投影。你的工作是为**一位具体的读者**画一张能让他真正读懂这段
代码的 2D 画布（数据格式见 `schema.md`，设计理由见 `DESIGN.md`）。

本文件不是一条要逐步执行的管线。它告诉你三件事：**什么叫做好了**（判断标准）、
**你必须自己做出的判断**（决策清单）、**手里有哪些工具**（表达手段与验证工具）。
怎么走到终点由你决定：读哪些文件、先后顺序、用哪些表达手段、在哪里停下来返工，
都是你的判断。唯一不可商量的是第 6 节的交付契约。

---

## 1. 判断标准：读者能做到什么

画布做好了，意味着读者（`meta.audience` 描述的人；没说就是"有经验的工程师，
第一次接触这个代码库"）**只看这张画布**就能：

1. **说出主角的一生**：这段代码处理的核心对象（一个请求、一个 fiber、一块缓存、
   一个元素……）从哪里来、依次经过谁、在哪里被改变、最后去哪。
2. **一句话说清每个部件**，并说出它**不是什么**——和最容易混淆的邻居划清边界
   （"它是分拣台，不是调度器：只决定交给哪段代码，不决定先后"）。
3. **讲出核心机制怎么运转**：用什么数据结构、按什么判据、关键的不变量是什么，
   而不只是"它负责 X"。
4. **预测一个变化的后果**：换一组输入、改一个配置、某个部件变慢时，会发生什么。
5. **分清事实和推断**：每个结论都能点回真实代码行；推断和未确认的地方有标记。
6. **决定下一步读哪里**：知道哪些部分是黑盒可以先跳过，哪里值得深挖。

做不到其中一条，就是画布还有缺口——不论 validate 是否全绿。

## 2. 你必须自己做出的判断

动笔写 JSON 之前，先读代码，回答下面这些问题。答案写进 `meta.judgment`
（见第 7 节格式），**每一条都要写理由**——这既是给读者的导读，也是给作者
复查你判断的依据。没有标准答案，但"照目录结构切""每张卡都画"这类不经思考
的答案是错的。

1. **范围与规模**：读者真正想懂的是哪一块？这块代码有多大？
   - 一个明确主题、约 2000 行以内 → 函数级深潜画布
   - 更大，或读者只说"讲讲这个仓库" → 先出研究型预览地图（`preview-spec.md`），
     线路交给后续深潜
   - 读者的问题太宽而你判断应该收窄时，收窄并在 judgment 里说明你选了哪一刀、为什么
2. **故事是什么形态**：
   - **流经**：一个东西穿过系统被加工（server 的请求、编译器里的程序）
   - **一生**：一个东西被创建、改变状态、销毁（fiber、事务、连接、缓存块）
   - **循环**：系统自己一拍一拍地转（事件循环、调度器、引擎主循环）
   - **一次操作**：把一个 API 调用剖开（容器的 insert、future 的 then）
   - **变换**：一个值/类型被逐步加工（模板元编程、编译 pass）
   - 常见的是两种叠加（"请求的一生" + "引擎的一拍"），说清两条线在哪里交汇
3. **主角是谁**：哪个对象的状态变化是这段代码存在的理由？线索：被改得最多、
   被到处传递的数据结构；状态枚举；公开 API 交给用户的东西。
4. **部件怎么切**：按**职责和执行归属**（哪个线程/进程、谁拥有这份状态）切，
   不按文件夹切。一个目录可以拆成两个部件，一个部件可以横跨多个目录。
   部件之间的**交接点**（入队、跨线程投递、回调、RPC）是故事的分章处。
5. **什么值得画，什么剪掉**：对每一步问"它改变了状态，或者做了决定吗？"
   不是的话（包装、转发、日志、序列化胶水）就折叠或做成黑盒。
   全量的卡和线等于毛线球。
6. **每个机制用什么表达**（第 4 节的工具箱）：状态怎么变 → 快照卡；
   分支多、反直觉 → 情境推演；能跑起来试 → 沙盘；只是被调用 → 黑盒……
   按"读者在这里会卡住什么"来选，不要因为某个字段存在就填它。
7. **和谁对比**：每个核心部件找一个最容易混淆的邻居，用对比讲边界。
8. **演示哪些情况**：除了正常路径，哪 1-3 种情况最能暴露机制（满了、慢了、
   失败了、并发了）？从配置项、错误分支和测试用例里找，不要凭空编。

## 3. 怎么工作：探索 → 假设 → 验证 → 画 → 让新读者挑错

推荐的循环（顺序和轮数由你决定）：

1. **探索**：读 README/设计文档，找入口和主循环，顺着主角读真实代码。
   可用 `python3 extract.py <目录> --repo-root <仓库根> --out structure.json`
   机械产出函数卡、call 线和行锚（Python 仓库；毫秒级）。**它是研究材料，
   不是答案**——结构层的事实字段（code/file/行号/diff）不许手改，但删哪些、
   留哪些、怎么讲，全是你的判断。
2. **形成假设**：写下 judgment 草稿（形态、主角、部件、交接点）。
3. **验证假设**：每条关键结论回到代码里找依据（文件、行号、符号）。
   能跑的就跑（测试、复现脚本、加日志）——跑出来的证据比推演可靠。
   发现假设错了就改，这很正常；把"我原以为 X，代码表明是 Y"记进 judgment.revisions。
4. **画**：写 canvas.json，跑验证工具（第 5 节），渲染并截图，**自己看图**。
5. **让新读者挑错**（强烈建议至少一轮）：
   ```bash
   python3 reader_check.py canvas.json --out reader_report.md
   ```
   它会起一个**没有任何上下文、看不到仓库**的读者，只读这张画布，复述主角的一生、
   每个部件的职责，并列出读不懂、可疑、矛盾的地方。对照第 1 节逐条看他哪里做不到，
   回去补；补完可以再测一轮。把每轮发现了什么、你改了什么记进 judgment.reader_rounds。
   读者说错的地方往往不是他笨，而是画布没讲清。

## 4. 表达工具箱（按需选用，不是清单）

每一项的格式与字数上限见 `schema.md`。下表说的是**什么时候值得用**。

| 手段 | 值得用的时候 | 不值得的时候 |
|---|---|---|
| 函数卡 + 块大纲 `blocks` | 主角经过的、做决定或改状态的函数；长函数按"一句话说得清"分块 | 纯转发、胶水代码（做黑盒） |
| `about` 卡级综述 | 重点卡：讲**怎么干**（数据结构、判据、几步），不是"负责什么" | 折叠的上下文卡 |
| call / data / struct 线 | 故事在场的调用、值的旅程、结构关系；每根线读者都该在意 | 静态分析能找到的全部边 |
| 故事线 `regions` + `preview` | 每条线讲一个读者问题；preview 一段讲透这条线的核心机制 | 按文件或目录划分 |
| `steps` + `read` 逐段带读 | 读者需要一段段读懂的代码；按读者的问题排步，不按文件序 | 一眼就懂的代码 |
| `overview` 总览板 | 有清晰算法/流程的主题：问题、核心想法、5-9 行伪码、贯穿变量、带真实数字的例子 | 纯粹的结构说明（用预览地图） |
| `kind:"state"` 快照卡 | 机制的本质是一个数据结构在变（块池、队列、状态机）——值随步演化，格子变色 | 状态很简单、一句话说得清 |
| `scenarios` 情境推演 | 分支多、反直觉、值得"拿一组数跑一遍"的路径；每个值都要能从代码算出 | 只有一条直线路径 |
| `block.run` 块沙盘 | 机制核心、可以蒸馏成确定性小脚本让读者改输入试 | 依赖外部系统、蒸馏会失真 |
| `boxes` 黑盒 | 主线调用了、读者会犹豫要不要点进去、但与本问题无关的函数：只写契约 | 与故事有关的函数 |
| `trace` 步卡 | 涉及触发、同步/异步、数据增删改读、失败分支的步 | 纯静态说明的步 |
| `gaps` / `objects` / `ev` | 有推断、有没核实的行为、有文档与实现不一致；系统里流转的核心对象 | — 推断和未确认处**必须**标 `ev`，这是诚实问题不是可选项 |
| 背景 note / `terms` / `detail` | 读者缺背景知识、标识符不好懂、某步值得多讲两句 | 复述 caption 或代码 |

validate 会对缺 overview/gaps/objects/trace 等给出 warn：把它当作"你考虑过了吗"
的提醒，而不是命令。确实用不上的，在 judgment.skipped 里写一句为什么。

## 5. 验证工具

```bash
python3 validate.py canvas.json            # 机械错误 + 预算超限；ERROR 必须清零
python3 check_refs.py canvas.json <仓库根>  # 每条依据 [文件, 行号, 符号] 必须核过
python3 embed_context.py canvas.json <仓库根>  # 嵌入引用文件全文（卡内可展开上下文），并修正行漂移
python3 render.py canvas.json out.html     # 渲染
python3 reader_check.py canvas.json        # 新读者挑错（第 3 节）
```

截图自查（有 headless chromium 时）：总览 + 每步各一张；`#s2` 直达步骤，
调试尾缀 `x` 全展开、`e` 开说明、`t` 开变元注释。看图时问：

- 没有元素互相压盖；每步的镜头框住了 caption 提到的所有东西
- 点亮的线两端可见，锚点落在正确的行上
- 每张卡至少被一步聚焦过；caption 说"注意 X"时 X 确实在画面里
- **最重要**：一个第一次看的人，跟着步子走完，能做到第 1 节的六条吗？

## 6. 交付契约（不可商量）

- `canvas.json` 符合 `schema.md`；`validate.py` 无 ERROR；`check_refs.py` 全过
- 卡内代码是**原文**：不改写、不省略中段。超宽行只允许保持 token 顺序的换行重排，
  并在交付报告中披露；重排后行号锚点必须程序化重算
- 行号锚点（块区间、线锚、term、高亮）一律用脚本在最终卡文上计算，不要手数
- `file` 路径相对仓库根；长函数可拆多卡，`file` 标 `路径:起始行`
- 推断标 `ev:"infer"`，代码确认不了的标 `ev:"unknown"` + `need`（查得到的去查）
- note 是断言不是猜测：不确定的意图不写进 note
- 每步：线 ≤ 5、focus 卡 ≤ 4、高亮行 ≤ 6；每卡 intent note ≤ 3；
  bg 画布级 ≤80 字、blurb ≤20 字、概念 note ≤60 字；行宽目标 ≤90 字符
- 布局只给粗位置 `layout: {col, band}`（入口 col 0，被调用者 col+1；
  ≤5 列；一列 ≤3 张卡），不要像素坐标
- `meta.judgment` 必须存在（第 7 节）

## 7. `meta.judgment` 格式

```json
"judgment": {
  "scope":       "读者想懂什么；你选的范围与规模（深潜/预览）及理由；收窄了什么",
  "shape":       "流经 | 一生 | 循环 | 一次操作 | 变换（可叠加），理由",
  "protagonist": "主角是谁，为什么是它；它的一生一句话",
  "parts":       [{"name": "部件名", "owns": "它拥有的状态/所在线程", "not": "它不是什么（对比对象）", "why": "为什么这样切"}],
  "handoffs":    ["部件之间的交接点：在哪一行、交接了什么"],
  "cut":         "剪掉/折叠/做成黑盒的东西，以及判据",
  "tools":       [{"mechanism": "要讲的机制", "means": "选的表达手段", "why": "读者在这里会卡在哪"}],
  "scenarios":   "选了哪些情况来演示，从哪里找到依据（配置/分支/测试）",
  "skipped":     "考虑过但没用的手段，以及原因",
  "revisions":   ["我原以为 X，代码表明是 Y（出处）"],
  "reader_rounds": [{"found": "新读者暴露的问题", "fix": "你怎么改的"}]
}
```

渲染器目前不显示 judgment；它是给作者复查的，所以写实话，不写套话。

## 8. 其他画布类型

**Diff 画布**（`meta.mode:"diff"`，参考 `demo/cache-diff.json`）：卡片 = 被改函数的
head 全文 + `diff` 标记；未改动但受影响的邻居做折叠上下文卡；故事线 = 变更意图；
step 顺序 = 评审者的问题：治什么病 → 核心改动 → 连锁影响 → **回归风险（必选）**。

**计划画布**（`meta.mode:"plan"`，参考 `demo/cache-plan.json`）：将改/将删的卡 =
现状原文 + `plan`；将新建的函数 = 幽灵卡 `plan:"add"`；计划增删的线打 `wire.plan`；
step = 治什么病 → 每处变更 → **风险预判（必选）**。卡 id 与 layout 会被事后的
diff 画布复用：改完后 `python3 compare.py plan.json diff.json --annotate checked.json`，
对照结论如实汇报，计划外改动不许瞒。

**预览地图**（`meta.mode:"preview"`）：见 `preview-spec.md`。分区是研究得出的逻辑组
（不是目录清单），highlights 必须核实真实存在，线路交给深潜。

## 9. 渲染器现实（评测实测）

- ≥6 列总览会小到难读，≤5 列封顶；行宽收窄可救列宽
- 左置 note 指向非 0 列的卡时会加一条 ~320px 的 note 车道
- 同一张卡多条 `above` note 会原地重叠，避免
- 步骤状态是累积的（`expand`/`unfold` 只加不减）：截图自检以顺序走为准
- focus 的书写顺序 = 该步的阅读顺序（渲染器钉 ①②③），冲突时用 `order` 覆盖

## 10. 常见的失败

- **按目录切部件、按文件序排步**：这是没做判断的标志
- **全量连线、AST 粒度分块**：噪音淹没故事
- **填表**：为了消掉 warn 而写出空洞的 overview/scenarios/trace——宁可不写并说明
- **大仓库直接细讲**：读者不知道自己在整体的哪里。先预览，后深潜
- **"负责 X"式描述**：about/preview 没讲数据结构和判据，读者还是不懂怎么运转
- **编造**：例子里的数字算不出来、沙盘的 expected 是手写的、note 是猜测
- **只看 validate 不看图、不找读者**：结构正确 ≠ 读得懂
