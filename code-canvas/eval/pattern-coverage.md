# 形状问卷实测：7 类代码、29 个模块

> 2026-11-15。问卷见 `../pattern-spec.md`，逐行原始作答见 `pattern-coverage.tsv`。
> 这是**一个人手工作答一遍**的结果，不是工具跑出来的，也没有测两次作答是否一致。结论的可信度按这个打折。

## 问的是什么

作者的假设：代码里的"公式"是有限的，可以固定下来，让可视化不必每次由模型判断。
上一轮我的回应是：具名 pattern 列不完，但**维度**可以封闭。这次验证两件事：

1. 五个维度（状态形状、执行者、控制交接、重复方式、模式变量）+ 游标 + 不变量，拿到没见过的代码上答不答得出。
2. 每个答案**能不能由语法决定**（M），还是要读懂语义（J），还是仓库里根本没有答案（X）。这决定了能省掉多少模型判断。

也就是说 v0 确实带着那类代码的偏见，上一轮作者批评的"只针对给的例子"在 v0 上仍然成立，只是轻了一层。
v0.1 的五处改动都是别的类别逼出来的。

### 能不能不靠模型

每格的评级标准：**M** = 语言或标准库层面的语法信号就能定；**J** = 要读懂语义，或依赖项目自定义的符号；**X** = 仓库里没有答案。

| 维度 | M | J | X | 不适用 | 说明 |
|---|---|---|---|---|---|
| 重复 | 19 | 0 | 0 | 10 | 循环节点类型 + 调用图成环，纯语法 |
| 选择 / 分派 | 19 | 0 | 1 | 9 | `switch`、下标调用、守卫；X 是 Django ViewSet |
| 状态形状 | 11 | 7 | 1 | 10 | C / Go 11 个里 10 个 M；Python / JS 8 个里 6 个 J、1 个 X |
| 模式变量 | 3 | 4 | 0 | 22 | 显式 enum 全 M（含转换表）；隐式全 J |
| 执行者 | 5 | 7 | 3 | 14 | Go `go` 语句 M；内核里靠读懂才知道谁在跑；框架里 X |
| 交接 | 6 | 6 | 1 | 16 | channel / 装饰器 M；`sleep/wakeup/swtch` 这类项目自定义原语 J |
| 游标 | 5 | 10 | 0 | 14 | 下标位置的变量能抓到，但"它是不是有意义的游标"多半要判断 |
| **合计** | **68** | **34** | **6** | 95 | 有答案的 108 格里 63% 可机械定 |

外加不变量：29 个里凡是有数据体的都要写，**全部**要模型。

所以对作者那句"不必每次都得 model 做判断"，实测给出的答案是：

- **控制结构（重复、选择）可以完全不靠模型。** 这是最确定的部分。
- **显式状态机可以完全不靠模型，连转换表一起。** xv6 `p->state`：enum 在 `proc.h:79`，11 处赋值在 `proc.c`
  （56、126、170、228、301、358、451、505、568、590、614），每处的外层条件和所在函数就是转换的起点和触发者。
  raft `cm.state`：`raft.go` 126、187、472、535、549。现在这张图是模型读完代码画的，其实可以直接抽。
- **并发结构在语言有原生语法时可以**（Go、async Python），没有时要模型认一次项目的原语，之后就能机械。
- **数据形状在有类型的语言里可以，在 Python / JS 里不行。**
- **游标、不变量、隐式模式仍然要模型**，但它从"决定画成什么"变成"往固定槽位里填一句话"，范围小得多，也更容易核对。

### 逐条发现

**A. v0 漏了"选择 / 分派"这一维。** xv6 `syscall.c:146` `syscalls[num]()`、chibicc `codegen.c:695` `switch (node->kind)`、
todo-react `App.jsx:59` `.filter(FILTER_MAP[filter])`——这三处的主要结构就是分派，v0 的五题里没有地方写。
事后看很明显：顺序、选择、重复是结构化程序的三件套，v0 只问了重复。

**B. 交接里漏了"等待-唤醒"。** xv6 的 pipe（`pipe.c:92` sleep、`:105` wakeup）、log（`begin_op` 里等 `committing` 清零）、bio、kalloc
都是"拿锁，条件不满足就睡，别人改了条件来叫醒"。它不是消息（没有数据在走），也不是回调。

**C. "模块"不是合适的作答单位。** `p->state` 的转换散在 11 个函数里，没有哪个"模块"是这个状态机；
raft 的 ConsensusModule 一个结构体里同时跑着选举定时器、心跳、AE 发送、提交通道四条流，各有各的循环。
答得顺的单位是两种：**数据体**和**执行流**，中间用"谁访问谁"连起来。这正好就是场景层已有的模型（thread 对 queue / store），算是一次独立印证。

**D. 变换型代码没有"持有的状态"，只有输入和输出的形状。** chibicc 四趟（`tokenize.c:490`、`preprocess.c:839`、`parse.c`、`codegen.c:692`）
是 字符序列 → token 链表 → token 链表 → 树 → 文本；nanoGPT `generate`（`model.py:306`）是序列每轮长一格。
v0 问"持有什么形状"，这些全答"无"，信息都丢了。

**E. 实现形状和逻辑角色常常不是一回事。** chibicc hashmap 是数组 + 线性探测 + 墓碑（`hashmap.c:15, 67`）；
xv6 bcache 是双向链表，但用法是"按块号查"+"按最近使用排序"（`bio.c:65-81, 128-132`）；
sortedcontainers 的 `_index` 是存在一维数组里的求和树（`sortedlist.py:256-258` `(child - 1) >> 1`）。
只答一个的话，要么图对不上代码，要么读者看不出它是干什么的。

**F. 框架代持——最大的洞。** `ArticleViewSet`（`articles/views.py`）全是类属性声明加几个短方法。
请求怎么进来、认证和权限什么时候跑、谁调 `create`，这些都在 DRF 里。四个维度答 X：不是难判断，是仓库里没有。
React 轻一些（组件里的 state 和回调答得出），但"什么时候重渲染"同样在框架里。
这类代码在真实仓库里占比很高，问卷对它们只能给出"框架调用我 → 一段流程图"。

**G. 领域想法。** attention 前向（`model.py:52`）按问卷只能答出"网格进、网格出、无循环无分支"，这是对的，也是没用的——
要讲的是那个下三角 mask 和 softmax 在算什么。chibicc 的 hideset（`preprocess.c:631`）同理：机制是"展开前查一个集合"，
值得讲的是"为什么这样就不会无限展开"。上一轮我预计会有这类，实测确认。

各记号出现次数：D 6、B 4、A 3、E 3、F 3、G 2、C 1。

## 这次没有回答的

1. **稳定性没有测。** 作者要的是"更稳定"。这次只验证了"答得出"和"多少可机械"，没有验证
   "同一段代码让 agent 按问卷答两次，结果是否比自由发挥更一致"。这才是命题本身，需要单独跑。
2. **M / J 评级是我读代码时的判断，没有写出提取器去证实。** "可机械"的那 63% 是上限估计；
   真写出来会遇到宏、间接调用、动态分派，数字会往下掉。
3. **样本小且是我挑的。** 29 个模块，都是各仓库里结构比较清楚的部分。胶水代码、配置驱动的代码、
   大型业务代码（几百个平铺的 handler）没有看。
4. **每类只有一个仓库**，且都是小而干净的教学级项目。
5. **没有画任何图。** §3 的"答案 → 画法"映射是纸面上的，有 5 处标了"要补"。

## 建议的下一步（按性价比）

1. **先做显式状态机的机械提取**（进 `extract.py`）：找 enum 型字段 → 收集赋值点 → 取外层条件 → 出转换表。
   范围最小、零 LLM、结果可以直接和现有 zoom 画布里模型写的 statemachine 对比，立刻知道"机械的"比"模型画的"差多少。
2. **重复 + 选择的机械探针**：同样进 extract，输出每个函数的循环 / 分派骨架。这两维实测 100% 可语法判定。
3. **两次作答一致性实验**：挑 5 个模块，自由发挥 vs 按问卷，各跑两次，比较两次产物的结构差异。
   这一步要花模型的钱（估计几美元），做之前先报预估。
4. **框架生命周期包**先只做一个（DRF 或 React），验证"固定骨架 + 仓库填槽"是否成立，再决定要不要铺开。

不建议现在做的：把问卷接进 zoom-spec 让生产 agent 用。在 1–3 有结果之前，它只是又一段提示词，稳不稳没有证据。
