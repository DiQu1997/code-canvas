## 1. 画了什么、为什么这么取舍

**画了 8 个框、9 条线**，排成一个圈，表示一步之内的活：

- 圈里是 A 常驻状态 → B 拼输入内核 → C 定长输入缓冲 → D 前向 → E 单槽暂存 → F 采样，用虚线框圈成「主 stream：A→F 按发射顺序串行」。
- F 有一条线 `post_update` 回到 A。这是全图的主角：它说明下一步的输入 token 不经过 CPU。
- 圈外有两个框：G「copy_stream 拷回」（`AsyncOutput`，单独圈成 copy_stream），和顶层过来的「引擎主线程」。
- 线 9「get_output · 晚一步」从 G 回到引擎主线程，说明卡点明这是 CPU 唯一真正等 GPU 的地方。

**推演**接着顶层的例子：槽 1023、block `[5, 6]`、S1 预填 20 个 token、S2 起每步 1 个。九步依次是：

1. 差量写入先暂存；
2. 拼 S1 的输入（守卫判断「还在预填」，不填上一个 token）；
3. 选 PIECEWISE 图、补到 24，`execute_model` 返回 None；
4. 采出 `<法国>`，拷贝排到另一条流；
5. `post_update` 写回槽位；
6. S2 拼输入时 GPU 自己从槽里读到 `<法国>`；
7. S2 用 FULL 图回放，采出 `<的>`；
8. 晚一步，CPU 才等 S1 的 event；
9. 收尾的空步，把槽还掉。

**没单独画成框的**：
- block table、UVA 暂存池、CPU 上的乐观镜像：放进说明卡。它们是细节，画成框会把主线冲淡。
- 「选哪张 CUDA graph」：并进「前向」框。卡里和推演第 3 步都说明了它其实发生在拼输入之前。
- 结构化输出的 `deferred_step`：它是引擎这一侧的变体，只放在「单槽暂存」的说明卡和一个源码页里。

**没有再做第三层机器图。** 每个框里面基本是一段从头读到尾的代码，所以直接落到 6 个源码页：常驻状态字段与占槽、`execute_model` 开头、拼输入内核、CUDA graph 分派、采样后拷贝与写回、`deferred_step`。

## 4. 推断和不确定的事实

**标为「推断」的「为什么」：**
- 拼上一个 token 放在 GPU 内核里，是为了让 CPU 不用等；
- 同一条 stream 按序执行，保证 S2 读到的是 `<法国>`；
- `wait_stream` 的必要性；
- 拷贝走单独一条流，是为了不挡住主 stream；
- 只对最后一个位置算 logits 的动机；
- 每步新建 event 的原因；
- 收尾空步本身是否存在；
- `pop()` 弹列表末尾、首个请求拿到槽 1023（底稿也没找到依据）。

**例子里的设定值**：槽 1023（基于 `max_num_seqs=1024`）、block `[5, 6]`、PIECEWISE 补到 24 都是底稿设的。其中「补到 24」是研究员按默认网格手推的，没有测试验证。

**底稿缺的**：S8 已经发射之后，它的结果在调度器那边怎么丢掉；底稿没讲，我也没写。

**底稿锚点偏差**：`docs/design/model_runner_v2.md` 里那句「Building these tensors from scratch…」实际在第 17 行，底稿写的是第 13 行。我按仓库原文用了第 17 行。
