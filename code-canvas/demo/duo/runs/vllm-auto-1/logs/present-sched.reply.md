## 报告：「调度器」框的下一层

**1. 画了什么、为什么这样取舍**

- **机器图（节点 `sched`）：9 个框、11 条线、15 步推演。**
  - 框：运行队列、等待队列、本步 token 预算、定这步排几个、KV 账房（`KVCacheManager`）、块仓库（`BlockPool`）、本步工单（`SchedulerOutput`）、收结果（`update_from_output`）。另有一个「请求的三个数」（已有 / 已算 / 占位），不接线，当放大镜用：它就是顶层框上那三个数，也是读者最该带走的那句「已算追已有」。
  - 线按 `schedule()` 的真实顺序画：先排 running → 再排 waiting（没抢占才排）→ 封顶 → 要块 → 取块 → 记工单 → GPU（晚一步）→ 追加、消占位 → 还块。另外画了「入场」和「抢占」两条，表示请求在 waiting 和 running 之间来回移动。
- **决定不画的东西：**
  - 「前缀缓存」没有单独成框。代码里它就是账房的 `get_computed_blocks` 加上仓库里的哈希表，单独画反而会让读者以为多了一个部件。
  - 「抢占」画成线，没画成框。它没有自己的状态，本质是一个请求从 running 挪回 waiting、同时把块还掉。
  - 旁支一律只在说明卡或源码页的说明里提一句：KV 连接器、Mamba、编码器、DP 节流、priority 策略的细节、watermark 等。
- **推演怎么走：**
  - 主线接顶层的例子 R（20 个 prompt token，`max_tokens=8`，第 7 个是 `<eos>`），走 S1 到 S8。
  - 中间插进底稿补设的三个场景：B（5000 token 的长请求 L 被切成 2047 / 2047 / 906）、A（同样的 prompt 再来一次，命中 16 个 token）、C（池里 10 块，踢掉 B）。这样预算、前缀缓存、抢占三块机制都能在推演里动起来。
  - 本页补设了 `block_size=16` 和预算 2048，都标了「设」。
- **再往下一层：**
  - 没有一个框值得再画第三层机器图。块仓库其实可以有一张（空闲队列两端、`ref_cnt`、哈希表），但这一趟只用小图加源码页表达，下面第 3 点里也说了。
  - 直接落到 5 个带批注的源码页：
    - `sched.loop`：开头的设计注释、预算、running 循环
    - `sched.admit`：waiting 入场
    - `sched.preempt`：抢占循环和 `_preempt_request`
    - `sched.kv`：`get_computed_blocks`、`allocate_slots`、`BlockPool`
    - `sched.ph`：占位符和 `update_from_output`、`check_stop`
- **顶层的勘误**写在 `top-fixes-sched.md`：顶层最后一步把引擎队列画成空的、把 GPU 画成空闲，但那时 S8 其实还在飞，结果回来后会被丢掉。顶层文件我没改。

**4. 推断和不确定的地方**

- **标了「推断」的「为什么」：**
  - 本步抢占过就不再排 waiting；
  - waiting 队首分不到块就 `break`，后面的也不排；
  - 预算按 token 数限、不按请求数；
  - 先定 token 数再要块；
  - EOS 之后那一步的结果走「请求已结束」那条分支被丢掉；
  - 还块时不用等 GPU stream 写完；
  - 场景 C 里「A 弹走的正是 B 的尾块，B 前 4 块还在缓存里」——这是我按「倒序还 + 队头弹」的规则自己推的，底稿没有逐块写出来，测试也没有断言。
- **我自己从代码推出来、不够有把握的值：**
  - 场景 B 里 L 每步分 128 / 128 / 57 块，是按 ⌈n/16⌉ 手算的，没有任何测试断言。
- **底稿没有的东西：**
  - 为什么在 V1 里重算比换出到内存开销更低（文档只说了一句，没讲原因）；
  - 三档默认预算值是怎么定的；
  - 「抢占过就不排 waiting」和 waiting 侧 `break` 的设计理由，仓库里都没有注释。
- **一处超出底稿原文的引用：**本步工单那张卡引了 `vllm/v1/core/sched/output.py:243` 的注释。它就在底稿给的锚点旁边，引文照抄自源码。
