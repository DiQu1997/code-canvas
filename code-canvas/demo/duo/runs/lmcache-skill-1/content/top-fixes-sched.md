# 顶层需要改的地方（来自「调度侧连接器」下一层，依据 research/manuscript-sched.md）

## 1. 推演第 10 步「B：拿到 768，下 RETRIEVE 工单」的「为什么」：FREE 放的不是「vLLM 已有的那段」
- 原话：「如果 vLLM 自己已有一段，调度器会对那段的锁发 `free_lookup_locks`；这里命中 0，不用放。」
- 为什么不准：提交 `60538a08` 之后，LOOKUP 从「vLLM 命中取整到 256」的位置查起，vLLM 已有的整块**根本不上锁**（服务端只刷新 LRU）；
  `free_end = vLLM 命中` 在服务端向下取整，B′（vLLM 已有 320）发的是 `[0, 320)` → 取整成 `[0, 256)` → 空，什么也不放。
  FREE 真放东西的是：不用取时放全部命中、LOOKUP 起点记得比最终 vLLM 命中低、APC 缩水后被放弃的 LOOKUP 区间。底稿 §0「上一趟之后代码有新机制」、§Q3、§Q5 的表和「FREE 什么时候真有东西可放」。
- 建议：「vLLM 自己已有的整块，LOOKUP 从一开始就跳过、不上锁；`free_lookup_locks` 放的是『查到了却用不上』的锁（例如根本不用取时放全部）。这里 768 全要取，不用放。」

## 2. 连线 `w_lock` 说明卡「容易看错的地方」第 1 条：同一个问题
- 原话：「放锁有三条路：RETRIEVE 拷完后的流回调；对 vLLM 自己已有的那段，调度器发 `free_lookup_locks`。」
- 为什么不准：同上（底稿 §Q3、§Q5、§5 第 3 条：调度侧发 FREE 的只有分配回调和多服务端取最小值时的尾部）。
- 建议：「放锁有三条路：RETRIEVE 拷完后的流回调；查到却用不上的（不用取时的全部命中、多服务端取最小后的尾部、APC 缩水后被放弃的 LOOKUP），调度器发 `free_lookup_locks`。」

## 3. 部件 `sched` 说明卡「容易看错的地方」第 2 条：「通常要隔一两个调度步」没有依据
- 原话：「命中数通常要隔一两个调度步才拿得到：LOOKUP 回执到了才发 QUERY，QUERY 回来了，下一次被 vLLM 问到时才交得出。」
- 为什么不准：底稿 §Q2 和 §7 第 1 条：下限是「下一步」（设 RPC 往返比一个调度步短），仓库里没有实测步数，「通常一两步」是没依据的说法。
- 建议：「命中数最早在下一个调度步才拿得到：……下一次被 vLLM 问到时才交得出。要隔几步取决于 RPC 往返和调度步的长短，仓库里没有实测。」

## 4. 推演第 8 步「A：报完成，回收 block」：先后顺序写反了
- 原话：「worker 的 `get_finished` 看到『回复已到 + event 已完成』，报 A 存完。A 结束时调度器因为发过 STORE，要求 vLLM 延迟回收 63 个 block，直到这份报告到了才回收……」
- 为什么不准：worker 只报「调度侧名单里有」的请求（求交），而名单是 `request_finished` 之后、**下一步**才随元数据到 worker 的；所以顺序是「A 结束 → 答延迟、进名单 → 下一步名单到 worker → worker 报 A 存完 → vLLM 回收」。底稿 §Q6「回收的完整链路（四跳）」、§2.2 的 sN / sN+1 两行。
- 建议：「A 结束时调度器因为发过 STORE，答『延迟回收』并把 A 记进名单；名单下一步随元数据到 worker，worker 确认 A 的 STORE『回复已到 + event 已完成』才报 A 存完，vLLM 这时才回收 63 个 block。同时发 `END_SESSION`……」

## 5. 部件 `sched` 说明卡「怎么设计的」第 4 条：存的算术少了下界（说法不全，不算错）
- 原话：「存多少：已算好的 token 取 vLLM 已有和 LMCache 已有的 max，封顶到 prompt 长度，减去已存的，够一整块才存。」
- 为什么不全：`computed` 外面还有一层 `max(…, num_engine_computed_tokens)`（vLLM 真实已算位置）作下界，提交 `4f7d283a`；底稿 §Q4。顶层例子的数不受影响。
- 建议（可选）：「……取 vLLM 已有和 LMCache 已有的 max（且不低于 vLLM 真实已算到的位置）……」
