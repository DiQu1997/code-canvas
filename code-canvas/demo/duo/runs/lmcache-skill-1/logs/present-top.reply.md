## 报告（讲解员 · 顶层）

### 1. 画了什么、为什么这么取舍

**框（7 个，分两组：vLLM 两个进程 / LMCache 服务进程）**：调度侧连接器、worker 侧连接器、vLLM 的 GPU 显存、查找模块、身份（滚动哈希）、传输模块、L1 存储。

**没画成框的**：
- **ZMQ 请求服务器和线程池（⑤）**：它只负责路由，单独画会多一层转发，读者却得不到新东西。所以把它拆进两条 RPC 线的说明卡：哪个线程池、亲和线程、为什么回复要回到主循环发。
- **LayoutDescRegistry、淘汰控制器、StoreController / PrefetchController**：分别放进 L1 和传输模块的卡里。
- **§8 那些旁路模式**：一律不画。

**线（8 条）**：
- 调度侧到查找模块的 LOOKUP（不等回执）
- 调度侧到 worker 的工单 LoadStoreOp
- worker 回调度侧的「完成名单」（虚线），用来讲延迟回收
- worker 到传输模块的 STORE/RETRIEVE + event
- 传输模块到 GPU 显存的 CUDA IPC 直接读写
- 传输模块到 L1 的「写入 / 读出并放锁」
- 查找模块到 L1 的「查 + 上读锁」
- 查找模块到身份框的「算哈希链」

**故意少画的一条**：传输模块到身份框。画上它，手机竖排时线会穿过别的框，只能交叉。所以在 w_hash 的卡里说明了「传输模块也走这一步」，A6 那步推演里也写了「重算出同一条链」。

**推演（12 步）**：用的是底稿的例子。
- 启动注册。
- 请求 A（1000 token）共 7 步：只查 [0,768) → 全 miss → 存 b0–b47 → staging → 转正，共约 108 MiB → 延迟回收。
- 请求 B（1200 token，前 900 同 A）共 4 步：h0–h2 命中，各上 1 把读锁 → 取回 768 → 拷完放锁 → 只算 432 个 token，再存 h3′。

各框中间的小图跟着这套数一起变。

**下一层的安排**：
- **直接挂源码页（3 个）**，因为它们本身就是一段从头读到尾的代码：
  - worker 侧：`start_load_kv` 和 `wait_for_save`
  - 查找模块：lookup 的 5 段关键代码
  - 滚动哈希：blake3 一块、Session 增量计算、身份字段
- **申请下一层（`dives.json`，3 条）**，因为里面各有一套自己的机制，底稿只讲到高层：
  - ① 传输模块：CUDA 流、event、staging、回调、亲和线程
  - ② L1 存储：对象状态机、TTL 读写锁、淘汰
  - ③ 调度侧连接器：tracker 状态机、存多少的算术、LookupState 怎么轮询

  查找模块没申请：锁怎么上、怎么放在 L1 那条申请里会讲到，它自己的代码已经挂了源码页。

### 2. 数字
- 构建 WARN **0**；排版问题 **0**（桌面和手机、三个图层、每一步都量过）。
- `--all`：**93 PASS / 2 FAIL**。两条 FAIL 都是「钻进去指到了未展开的空页」，对应 sched / xfer / l1 三个申请中的槽位，这一趟本来就该是空的。三个源码页都没有错误。
- 截图用了 **2 轮**：第 1 轮截顶层完整的一套，第 2 轮跑 `--all`。之后只改了两条源码批注的文字，用 `--check` 复查过。

### 3. 自己看图觉得还不够的地方
- **锁的生命周期还是分散的**。上锁、用锁、放锁分在 3 条线、2 步推演里，没有一处集中呈现，读者可能要来回翻。这要等 L1 那一层补上。
- **手机上 LOOKUP 线的位置**：手机竖排里，LOOKUP 那条线从左上斜跨到右侧，身份框又在右上角，第一眼不太好分清哪边是 vLLM、哪边是服务端。手机上没有分组框，舞台的分组只画桌面那一套。
- **L1 框比较空**：开头它的空白很多，后面几步才填上内容。
- **「为什么」图层有 15 条、「易混点」有 14 条**，信息密度偏高。不过框底那句话都控制在两行以内。

### 4. 推断和不确定的地方
- **标了「推断」的「为什么」**：
  - 让服务端自己拷、vLLM 不用 synchronize
  - 查到就要锁，否则会被淘汰
  - 必须等拷完才转正 / 放锁
  - 链式哈希等于整个前缀相同
  - 「决定在调度器、动手在 worker」
  - 生成的 token 不值得存

  这些和底稿里标【推断】的地方一致。其中「决定在调度器、动手在 worker」是我自己加的推断，底稿没有这句。
- **36 MiB / 108 MiB** 是底稿根据设定的模型形状推算出来的，卡里已注明「按设定的模型形状推算」。
- **3 条原本是「文档」级的理由被降成了「推断」**：独立进程没有 GIL 开销、锁带超时防死锁（出现了两次）。原因是舞台不收 `.rst` 锚点，见第 5 条。卡里已写明出处是 `docs/source/mp/index.rst`。
- **缺的事实**（顶层用不上，下一层会用到）：底稿没讲完成 event 在服务端流上的哪个位置录，也没讲拷贝内核怎么做布局转换。这两点已写进 xfer 那条申请的 ask 里。

### 5. 舞台问题（已记在 `framework-issues-scene.md`）
1. **锚点白名单不含 `.rst`**：引用 `docs/source/mp/index.rst` 会直接 BuildError，整个顶层退回临时骨架。这个仓库的设计文档都是 `.rst`。
2. **「按顺序读，下一页」那张卡显示错位**：上半部分是一个空的蓝色描边条，标题落在条外下方。在 d1-overview 和 d6-dive 两张截图的右下角都能看到。
3. **手机版没法画分组框**：这只是想要的功能，不确定舞台支不支持，我没去试。
