## 报告：「传输模块」下一层（`xfer`）

### 1. 画了什么、为什么这么取舍
- **一张 7 个框的机器图**，围绕底稿那句核心：「**亲和线程只排队下单，服务端 CUDA 流真正搬数据，排空线程在拷完后收尾**」。这一层的框有：亲和池 → 亲和线程（①）→ 拷贝路径（②）→ 服务端 CUDA 流（③）→ 排空线程（④），两头是框外的 worker 和 L1。连线 9 条，最要紧的两条是虚线「回句柄（未拷完）」和「host 函数」。
- **最主要的那张小图**是「服务端 CUDA 流」：画成一条从上往下的队列，GPU 从队头取。推演时，亲和线程一行一行往里排（等 ev_A → 放导入 ev → 拷 h0/h1/h2 → ★录 ev_done → finish_write），然后 GPU 逐行打勾。读者能直接看到「函数已经返回，队列还没走完」和「ev_done 排在提交前面」。亲和线程的小图是 5 项检查，逐步变成 ✓。
- **两个 event 起了不同的名字**（ev_A / ev_done），方向相反，写在 worker 卡的「易混点」里。
- **推演 12 步**，接着顶层的数走：A 存 `[0,768)`，48 个 block，h0/h1/h2 各 36 MiB，每层每块 32 KiB 刚好卡在 direct 的门槛上。第 1–9 步是 STORE，第 10–11 步是 B 的 RETRIEVE（和 STORE 对照：先定好要放的锁、`batch_size=4`、成功失败都放锁），第 12 步是 B′（skip 64 个 token = 4 个 block）。
- **框下面直接接源码页，没有第三层机器图**：亲和线程 → STORE 源码 / RETRIEVE 源码；拷贝 → 路径选择 + 32 KiB 门槛 + staged 循环 + CUDA 内核 + 测试；排空线程 / 流 → 回调链（Python 登记 + C++ host 函数 + 排空循环）；亲和池 → 亲和池源码。worker 框链到顶层已有的 `worker_src`。理由：这几块里面都是一两个能从头读到尾的函数，再画一层图只会把卡片上的话重复一遍。
- **没画的**：
  - `cache_context` 不单独成框：只有它挂着的流和缓冲有用，并进了流、亲和池两张卡。
  - event IPC 后端不单独成框：放进 worker 卡和「等·录·挂回调」那条线的卡。
  - unfull chunk、滑窗 / Mamba、ROCm 主机等待、GDS 都没画（底稿也建议这一层不展开）。
  - L1 不加链接：`l1` 槽位还没填。
  - 中途失败（abort_write）没做成推演步骤，只写在卡片和源码批注里，免得读者把一个假设的情况当成主线。

### 3. 我觉得还不够好的地方
- **手机上**：有 3 条长线（回句柄、等录挂、预留）要跨过中间的框，只能沿屏幕两侧走。因此框宽只剩 200，侧边线的「易混点」短句被压成「留导入」「缺≠败」「未存好」这种三个字，读者得点开卡片才懂。
- 「拷贝」框里面的平铺规则（block j → token j×16）只在文字和小图的映射里讲了，没有画成格子。
- 推演第 8→9 步之间「worker 已经报完成，L1 却还看不见」的时间差，靠的是文字和两张小图对照，没有一根直观的时间轴。
- 顶层推演第 5–7 步和这一层的 1–9 步是同一件事，对应关系只在两处 beat 的文字里点明了。

### 4. 推断和不确定的地方
- **标了「推断」的**：
  - STORE 为什么必须每批 1 块；
  - 完成 event 为什么建得那么早；
  - 完成 event 为什么录在提交回调之前；
  - staged 路径为什么要经过 GPU 暂存；
  - 死锁到底是谁拿着什么在等谁；
  - 例子到底走 direct 还是别的路径（取决于 CUDA 版本）；
  - 同一条流里的队头阻塞；
  - `try` 管不到 GPU 上异步出的错；
  - `finish_write` 失败后对象留到写锁超时（600 秒）。
- **用了但可能误读的**：测试 `test_l1_owner_completion.py:193` 钉住的顺序来自一个 **2 个 chunk、失败的 STORE**，最后一个回调是 `abort_write`。我在卡片里写明了，但推演第 6 步引它，是把它当「顺序」的证据用的。
- **底稿里缺的**：守卫失败时为什么回一个真 event 而不是空句柄；轮询间隔为什么是 5 ms。都已照底稿 §7 写成「没查到」。
