## 1. 画了什么、为什么这么取舍

**中间是账本，四个回调围着它。** 底稿最强调的是「跨好几个调度步、靠账本上的字段接力」，所以把每个请求的那本账放在中间，6 行值（state、vLLM 命中、LMCache 命中、已下单存、block、已调度）随 ▶ 一起变。四个 vLLM 回调按 ①②③④ 排在四个角，各自连到账本：
- ① 问：能取多少
- ② 分配后：定岔路
- ③ 每步出单
- ④ 结束：延迟回收

上面一条是「查找适配器（LookupState）⇄ LMCache 服务」，用虚线表示回复是在调度步之间、在别的线程上推进的。下面是「本步元数据」：工单和延迟名单都从这里送到 worker。

**不画的：**

- **「问」框上表示反复被问的回环。** 手机 340 宽、两框并排时，两侧都没有回环需要的空地。改成在框里的小图写「第几次问 / 答 None」。
- **worker 框和它的回报线。** 顶层的「完成名单」那条线已经讲过，这里放进说明卡和推演第 8 步。
- **单独的「工单工厂」框。** 并进了「每步出单」：存多少、取多少的算术放在那个框的小图和说明卡里。

**没有更深的一层机器图。** LookupState 里虽然也有一个小状态机，但它就是一个类里的几个函数，适配器框的小图已经能看到它在推进，所以直接落到源码页。6 张源码页都带逐行批注，批注用的是同一套数（A 1000、B 1200、B′ 320）：
- 账本字段和状态枚举

- 分配回调加出取单（GetRetrieveMetadata）
- 存单算术（GetStoreMetadata）
- 结束到延迟回收的四跳

顶层图里的「LMCache 服务」框直接钻到顶层已有的 `lookup_src`。

**推演：** 接着顶层的 A 和 B，步号 s1、s2… 是底稿设的，只表示先后。
- **A（只存）：** 第 1 次问 → 两步之间回复定下来 → 拿到 0 → 分 63 个 block → 出 STORE `[0,768)`、当场记账 → 解码期间 232 < 256 不出单 → 结束要求延迟回收 → 下一步名单才到 worker。
- **B（先取后存）：** 拿到 768 → 岔向「要取」、不发 FREE → 出 RETRIEVE 单（B 这一步并没被调度）→ 取完后第二次分配只追加 27 个 block、出 STORE `[768,1024)`。
- **B′（vLLM 自己已有 320）：** 查找起点 256 → FREE 放了个空 → 取回时 skip 64。

**只放进说明卡和源码批注、没进推演的：** B″（APC 缩水）、整段命中时少报一个 token、BYPASS、抢占、分块预填。理由是宁可少而清楚。

## 3. 我看图后觉得还不够好的地方
- **手机上第一屏是「LMCache 服务」和「查找适配器」**，中间的账本要往下滑才看到，读者可能先抓不住重点。
- **快照说明只在图注里。** 读者如果不看图注，可能以为图上的值就是推演的起点。
- **15 步偏长。** B′ 的两步和前面 B 的步骤换了一套数，读者可能会混；第 14 步标题已写「换个 B′」。

- **最常被误会的是「下单即记账」这件事**（存失败了账本不知道，也不会补存），目前只在卡片和批注里讲到，图上没有专门的表达。

## 4. 推断与不确定
下面这些「为什么」都标了「推断」：
- 为什么账本是唯一能跨步接力的地方。
- 为什么岔路要放在分配之后。
- 为什么查询发送写成「已发过就不重发」。
- 为什么延迟名单要绕元数据走一趟（`store_scheduled` 只在调度侧）。
- QUERY 为什么必须等回执之后才发（不等的话可能查不到任务）。
- 回收大约晚一步。
- 「下一步就能拿到命中数」：仓库里没有实测步数。
- 取单跟着账本状态出、而不是跟着「请求被调度」出（看循环遍历的是全部账本得出）。
- 被 vLLM 已覆盖的前缀按命中计入，如果它在 LMCache 里被淘汰了，这个请求不会补存。

底稿里缺、我也没有补的事实：
- 取消的请求为什么不发 FREE（是有意还是遗漏）。
- 出单时为什么先出取单再出存单。
- APC 为什么会缩水。

这些在卡里都写的是「底稿没查到」。

**顶层有 5 处说法不准**，写在 `top-fixes-sched.md`，交回顶层讲解员统一改：
1. 推演第 10 步「为什么」和 `w_lock` 卡都说「对 vLLM 已有的那段发 `free_lookup_locks`」。按新机制，那段根本没上锁，FREE 在这种情况下常常什么也不放（这两处共用一个原因，分两条写）。
2. 说明卡里「通常隔一两个调度步」没有依据，底稿只说下限是下一步。
3. 推演第 8 步「报完成、回收」的先后顺序写反了：实际是 A 先结束、进名单，下一步名单到 worker，worker 才报。
4. 存单算术少说了外层下界（vLLM 真实已算位置）。这一条是说法不全，不算错，顶层例子的数不受影响。
