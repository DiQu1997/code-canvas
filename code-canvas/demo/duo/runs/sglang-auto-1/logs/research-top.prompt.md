## 这一趟底稿的用途和深度（范围由此定，别研究过头）
这是第一趟研究：讲解员会据此做**顶层那一屏**——一张「机器图」（大约 6–10 个部件 + 它们之间的连线）、每个部件 / 每条连线一张说明卡（这里是干什么的 / 怎么设计的 / 为什么这么设计、好处是什么 / 容易看错的地方），以及一段拿具体例子、带具体的数走一遍的**逐步推演**。读者看完顶层，会想点进某几个框往下看；那时系统会另派研究员专门补研究那几个框，所以这一趟**不必**把每个框的内部研究到底。

所以底稿的深度按这个用途定：
- 讲清回答这个问题需要的**每一个参与者**（进程 / 线程 / 模块 / 对象 / 存储 / 数据结构）：它是谁、拿到什么、做了什么、交给谁什么。每个参与者落到几处关键锚点即可，不需要逐行讲函数。
- 参与者之间的**交接**（函数调用？队列？共享状态？跨进程？谁等谁？）同样重要——讲解员要把它们画成线。
- 给一个**贯穿全程的具体例子**，带具体的值（输入长什么样、被变成什么对象、中间状态怎么变、最后产出什么）。值如果是你为了讲解设的（不是代码里的常量），标明是设的。
- 先定「主路」：默认配置下最常见的那条路讲透，选哪条、理由是什么，写在开头。其它模式 / 旁路只用一小节点名：有哪些、从主路的哪里岔出去，不展开。
- 对每个参与者，用一两句话说出它**里面**大概有没有一套值得单独研究的机制（读者可能会想点进去的那种），给出入口锚点；不展开。
- 篇幅 **3 万字以内**，宁可少而准。超出这个用途的细节一句话带过并给入口锚点即可。

- 微观：边界与守卫；在接哪个底层错误；维护哪个不变量；顺序依赖（为什么 A 必须在 B 前）；并发与重入；生命周期与所有权；性能手法；魔数与阈值；语言 / 平台怪癖；历史补丁；防御与断言；只在某种情境才走的分支；观测 / 测试钩子。

## 硬约束：不许编
- **"怎么做"的每个断言**（分支、循环、调用、字段读写、顺序、谁发给谁）都要带锚点 `文件:行号`（或行号范围），锚点必须在 HEAD 上成立。
- **每一条"为什么"都要标来源等级**，五选一：

  - 【推断】你自己的推理，没有直接证据——必须说清是推断，以及推断依据
- "可改进处"一律标【观点】。
- 引用的原话必须**逐字照抄**（不翻译、不改写），讲解员那边的构建会逐条机械核对。
- 查了但没找到理由的地方，单列一节如实写「没查到为什么」，不要用一个听起来合理的说法补上。
