## 报告：「模型前向 + 采样」的下一层（`model_fwd`）

内容在 `content/content_model_fwd.py`。最终数字：我这两张图构建 WARN 0 条、排版问题 0 条，`--all` 456 PASS / 0 FAIL，截图用了 2 轮（第 2 轮就是 `--all`）。

### 1. 画了什么、为什么这样取舍

**第一层 `model_fwd`：一张机器图，10 个框 + 9 条线，没有塞满整台机器。**
- **框**：①这一批进来 → ②打包 → ③怎么跑：三选一 → ④模型躯干：逐层 attention ↔ ⑤页表 + KV 池 → ⑥只取最后一位 → ⑦采样 → 两个出口：⑧留给下一步（`future_map`）和 ⑨拷回 CPU。旁边还有一个「三条 CUDA 流」框，不连线，它的小图跟着推演点亮哪条流在干活。
- **KV 读写拆成两条线**（「写 k/v」看 `out_cache_loc`，「按页表读」看整行历史）。底稿特别提醒这两条容易混在一起。
- **三条路（decode 图 / prefill 图 / eager）不各画一个框**，压成一个判断框，小图是三行判断。原因：画成三个框要多 5 条线挤在同一个缝里，标签叠在一起；而且三条路跑的是同一个模型，真正不同的是「图里装什么、按什么分档、怎么补齐」。这个机制放到第二层去讲。
- **推演 11 步**，接顶层同一套数：请求占 `req_to_token` 第 3 行，前缀槽 37…41，新分 212…226，位置 5…19，采到 X1。第 n 圈 prefill 走 7 步（命中档 16、补 1 个 token）。第 n+1 圈 decode 走 3 步（分槽 227、输入从 `output_tokens_buf[3]` 取、档 1、整段回放、采到 X2）。最后 1 步是底稿设的对照：running 里有 5 个请求时补到档 8，3 个假请求指向第 0 号。

**第二层 `model_fwd.graph`「图回放里面」：只给「三选一」这一个框做了下一层图。**
- 只有这里有一套会变的状态：档位表、静态缓冲（真行和假行）、第 0 号、录好的图、切片。
- 上半是 decode 图，用 5 个请求补到档 8 的对照；下半是 prefill 的 breakable 图（15 个 token 补到档 16、躯干分段、attention 是断点、logits 在图外 eager 跑）。两条路最后汇到同一个图外的采样器。
- 推演 8 步。

**落到 8 个源码页**：总管、打包、三选一、attention（带 logits 那一小段）、采样、三条流（`run_batch` 的 overlap 分支）、decode 图、prefill 图。

**刻意没做的：**
- **attention、采样器没有再做一层图。** 它们基本是从头读到尾的一段，说明卡加源码页就够。
- **流水线并行的非末级 rank、投机解码、DP-attention、LoRA、多模态没画。** 底稿没展开，只在卡里点了一句。
- **推迟采样、WAR 屏障只写在说明卡里。** 它们是旁路，不在主路上。
- **「future_map → 下一步输入」这条回程线删掉了。** 手机上没有地方走线。改成推演第 8 步把入口框的小图换成 `[X1] ← future_map`，并在卡里讲。

### 3. 我觉得还不够好的地方
- **「什么在图里、什么在图外」靠卡片和推演文字讲。** 机器图上没法把框画成「在图里」的嵌套，读者可能要来回翻两层才对得上。
- **第一层推演 11 步偏长。** decode 那几步和 prefill 结构相同，读者可能嫌重复。
- **手机上「隐藏状态」那条线从右侧绕过 KV 框。** 能看懂，但不太直观。
- **我们这条请求的行号对不上。** sched_loop 那一层把请求 A 设成 `req_pool_idx=7`，我的底稿设的是第 3 行。我按我的底稿用了 3，读者在两个下层之间会看到两个行号，需要统一。

### 4. 推断、不确定、底稿缺的
- **标了「推断」的「为什么」：**
  - decode 为什么能用图（形状只由 bs 决定）；
  - 为什么断点断在 attention；
  - 采样为什么不录进图；
  - 先写后读的顺序；
  - future_map 靠同一条流天然有序；
  - 回放省的是 CPU 一个个发 kernel 的开销；
  - 小档密、大档疏的原因。
- **底稿明说没查到的：**
  - 档位步长为什么这样取；
  - 补齐上限为什么是 2 倍；
  - FA3 的 fill 值为什么是 1；
  - 推迟采样为什么默认关；
  - prefill 的 H2D 为什么推迟到 forward 流。
- **底稿之外看到、但没用的一条原文：** `prefill_cuda_graph_runner.py:198-200` 有一段注释（"A replay executes every padded token in its capture bucket..."），正好解释补齐上限存在的理由（不是为什么取 2）。底稿没收这条，我没用。研究员可以确认后补进去。
- **按代码写得更严的一处：** 「extend 长度元数据由 kernel 写」在代码里有条件（`_kernel_writes_metadata`），我写成了「设备支持时」。

### 5. 舞台问题
已记在 `framework-issues-model_fwd.md`：
1. 一条线没法「只在桌面画」，手机上长回程线没有走廊。
2. 说明卡的字数上限把锚点路径按全长算，带两个长路径的条目很容易超。
3. `g_checks` 没有中性的「没选这条分支」状态：`'no'` 画成红 ×，会被读成失败。

**顶层的事实错误（只报告，没改）：** 顶层「模型前向 + 采样」卡里写「prefill 通常走另一条路」。在 HEAD 上，CUDA 默认 prefill 也回放 breakable 图（第二份底稿 §8 已更正）。我在下层「三选一」的易混点里写了这条更正。
