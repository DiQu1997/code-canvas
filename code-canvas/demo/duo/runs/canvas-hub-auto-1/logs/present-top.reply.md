## 1. 画了什么、为什么

**9 个框。** 首页表单、/generate 把关、起任务（`spawn_generate`）、共享仓库缓存、生成 agent、服务端收尾（`post_pass`）、任务账本（`.jobs/`）、画布库、读者浏览器。桌面排成三排，按顺序走：第一排在服务进程里同步执行，第二排是后台脚本，第三排是入库和读者打开。手机上竖着排，任务账本单独放在右边一列。
- 把「任务账本」画成一个独立的框，是为了钉住底稿说的头号误会：服务和任务之间没有队列也没有回调，交接全靠文件。所以三条线都汇到它这里：起任务时写账本、收尾时写 `.status`、首页每 5 秒来轮询（虚线）。
- 「起任务 → 缓存」画成虚线「Popen 后放手」，表示服务把任务扔出去后就不管了。agent 身上画了一个虚线回环「自查、返工」，配合「服务端收尾」一起说明校验有两层：agent 自己查一遍，服务端不信任它再查一遍。

**没画成框的：** 7 种旁路（预览地图、动画缩放、升级、codex、粘贴代码、问答、duo）、`extract.py` 和 `reader_check.py`。它们要么不在主路上，要么只是 agent 手里的工具，放进说明卡就够了。

**推演用的例子：** 用底稿 §3 的 nano-vllm +「讲讲调度器怎么工作」，走 10 步，值都是底稿里的：任务编号 `j20261123-101530-482`、缓存目录 `nano-vllm-155c1586`、10 张卡 / 11 根线 / 6 步、x=40、y=720。小图里的值会跟着推演变，比如 `.ready` 从 ✗ 变 ✓、`.status` 从「—」变成 0、首页显示 done。

**直接挂了源码页的（都是一段从头读到尾的代码）：** `/generate` 分支 1112-1162、`spawn_generate` 分五段、缓存的四种取用方式 715-734、`list_jobs` 439-465、`post_pass` 608-637。

**申请了下一层的（按优先级）：**
1. **生成 agent**：SKILL 里的 8 个判断、自查循环、新读者挑错，是最核心、耗时最长的一步。
2. **读者浏览器排版**：「画布是 agent 画的」是最大的误会。
3. **服务端收尾**：embed 的行漂移修正、check_refs 的降级、validate 的规则和沙盘真跑。

「起任务」里那套 rc 在三段脚本间的传递，源码页加批注已经讲得清，所以没申请下钻。
