# canvas-duo：在本机跑「研究员 + 讲解员」

**你在这里是调度员，不是作者。** 画什么、讲什么、哪些框往下钻，全由 `run.py` 起的 agent 决定。
你只做五件事：**预检 → 报价、等用户点头 → 开跑 → 盯进度 → 验收并如实报告**。

- 不替 agent 写内容；不改运行目录里 `research/`、`content/` 的任何文件；不手改产物 HTML。
  产物有错就照实报告。修画布内容、修舞台，是这套系统的开发者的事，不是你的。
- 诚实高于一切：失败、超预算、agent 自己承认的短处，都原样告诉用户，不粉饰。

下文 `<SKILL>` 指本 skill 的目录（系统告诉你的 Base directory）。命令一律用 `python3 -I`。

## 1. 弄清三样东西

- **仓库** `REPO`：默认当前目录所在 git 仓库的根（`git rev-parse --show-toplevel`）。
- **问题** `Q`：用用户的**原话**，不改写、不翻译、不替他补充。用户没说问题就问他想看懂什么。
- **运行目录** `OUT`：默认 `~/canvas-duo-runs/<仓库名>-<YYYYMMDD-HHMM>`。
  它**不能**在被讲的仓库里，它和它的上级也不能有 CLAUDE.md / AGENTS.md：agent 的工作目录就是它，会把这些当成指示。
  预检会查这一条。成品名 `NAME` 默认 `<仓库名>-canvas`。

## 2. 预检（必须 0 FAIL）

```bash
python3 -I <SKILL>/preflight.py --repo "$REPO" --out "$OUT" --probe
```

- `--probe` 会真起一次 claude（便宜一档模型，上限 $0.50，实测 $0.04；第一次冷启动可能到 $0.1），验证两件事：登录可用；无人值守模式下 agent 读得到工作目录外的仓库。
  同一台机器第一次用时必加，之后可以省掉。
- **FAIL** 照提示修，修好再跑预检。改用户的环境（装包、改 PATH）要先问用户。常见 FAIL：
  - 找不到 playwright：用环境变量 `CANVAS_TEST_PW` 指到包的路径。
  - 浏览器起不来：用 `CANVAS_TEST_CHROMIUM` 指到一个 Chromium 可执行文件。
  - claude 太旧：缺 `--max-budget-usd`，更新 claude。
- **WARN** 要讲给用户听。最常见的是工作区有没提交的改动：构建和核对读的是 HEAD，agent 读的是工作区，改过的地方会对不上。
  建议用户先提交，或者在一个干净的 worktree 上跑。

## 3. 报价，等用户点头

开跑前告诉用户下面这些，**等他明确同意**再开跑。如果他在这次请求里已经给了预算并说了直接跑，就不用再问。

- 已有三次真跑的记录，都是默认模型配置、最多往下钻 3 个框：
  - sglang：$45.69，中途断过一次又接着跑；
  - vllm：$32.64，87 分钟；
  - code-canvas 自己：$25.17，78 分钟。
- 典型 $25–45，预算上限默认 $55：超了就不再起新 agent，已在跑的会跑完。
- 用的是本机 claude 的登录（订阅额度或 API 计费都会算进去）。
- 仓库代码会发给 Claude 处理，和平时用 Claude Code 读这个仓库一样。
- 成品 HTML **嵌着仓库源码**，按仓库本身的保密级别对待：不要上传、不要发到 hub 或公开链接。

用户要省钱时可以：
- `--max-dives 1` 或 `2`：少钻几个框；
- `--budget <美元>`：压低上限；
- `--models research_top=sonnet`：顶层研究员换便宜一档。这个组合没真跑过，质量没验证过，要告诉用户。

## 4. 开跑（后台）

```bash
mkdir -p "$OUT"
nohup python3 -I <SKILL>/run.py --repo "$REPO" --question "$Q" --out "$OUT" --name "$NAME" --budget 55 > "$OUT/run.log" 2>&1 &
```

- 用后台方式跑（Bash 的 run_in_background），不要前台阻塞一个多小时。
- 中途断了（机器睡眠、会话结束），**原样再跑同一条命令**就是接着上次：已成功的步骤直接跳过，已花的钱照算。
- 预算不够时不要自作主张加预算，先问用户。
- `claude` 不在 PATH 里时，加 `--cli-bin <路径>`。
- 预检时用了 `CANVAS_TEST_PW` / `CANVAS_TEST_CHROMIUM` 的，开跑命令前面也要带上同样的变量（`CANVAS_TEST_PW=… nohup python3 …`）。
  讲解员 agent 自己跑截图自检，用的就是这个环境。

## 5. 盯进度

进度一行一条写在 `$OUT/progress.txt`。用户问起时读它的最后几行，转述现在在哪一步、已花多少。大致节奏：

1. 顶层研究员：约 10 分钟；底稿核对不过会自动返工一次。
2. 顶层讲解员：约 12 分钟；它决定往下钻哪几个框（`content/dives.json`）。
3. 每个框：补充研究约 10 分钟（依次跑），下层讲解约 15–20 分钟（并行）。
4. 下层报回的顶层问题交回顶层讲解员改一次，约 2 分钟。
5. 装配 + 全量自检：约 5 分钟。看到「结束：花费 $…」就是跑完了。

等的时候用一个后台等待（循环检查 `run.py` 进程还在不在，进程结束后再读 progress.txt），不要每隔几十秒轮询一次。

## 6. 验收，如实报告

跑完后读 `$OUT/report.md`，再读 `$OUT/logs/` 里各位讲解员的最终回复 `present-*.reply.md`，每份都有「还不够好的地方」「推断和不确定」「舞台问题」几节。

给用户的报告包含：

- **成品路径**：`$OUT/$NAME.html`，自包含，浏览器直接打开，桌面和手机都能看。
- **花费、用时、每步模型**：照 report.md 抄，不估。
- **结构**：顶层画了什么；往下钻了哪几个框，各自为什么钻（report.md「往下钻」一节）。
- **机械结果**：底稿核对是否通过、`build --strict` 的 WARN 数、`shot_scene --all` 的 PASS / FAIL。哪项没过就直说哪项。
- **agent 自己承认的短处**：从各份 reply 里摘要转述，不要删掉难听的。
- **你自己的抽查**：挑 2–3 条页面上的具体说法（某个函数怎么做、某个数怎么来），去仓库源码里核对，报告对上了还是没对上。
  只核对、只报告，**不改**。
- **舞台问题**：`content/framework-issues-*.md` 是讲解员记下的工具问题，转告用户「这些要回 code-canvas 仓库修」。

## 7. 不在本 skill 里的

- **按反馈改版**（`revise.py`）：它的把关要用 code-canvas 仓库里的回归语料和 git，在这里跑不了。用户对画布有意见就记下原话，带回 code-canvas 仓库处理。
- **接进 canvas hub**：本 skill 就是给不方便上 hub 的仓库用的。
