# duo 实验：研究员 + 讲解员（Redis 淘汰 v1）

> 实验品。**没有并入工具链**（不走 validate / render / serve，不上 hub），没有自动化测试。
> 目的是先看一次「两个 agent 分工」能做出什么效果，再决定往哪优化。

问题：**Redis 内存超过 `maxmemory` 之后怎么腾内存、为什么这么做**（`performEvictions()` 一条线）。
仓库 `redis/redis` @ `fd7710ca2`（源码不入库，构建时要一份 clone）。

## 为什么做这个（方向转折）

前一阶段（`demo/generalize/`、`cfg` 图元）走的是「把程序压成固定 pattern → 固定图元」。作者的判断：
那是 **workflow 不是 agent**——切点、命名、用哪种图，都不该由我们写死。于是拆成两个角色：

| 角色 | 输入 | 输出 | 约束 |
|---|---|---|---|
| 研究员 | 一句问题 + 仓库（可用 git blame / log） | 一份**文字底稿**：怎么做的 + 宏观/微观的「为什么」 | 每个论断带 `文件:行`；每个「为什么」带证据等级 |
| 讲解员 | 底稿 + 仓库 | 一张自顶向下、可递归下钻的画布 | 代码必须是仓库原文；锚点 / 引文 / 提交机械核对 |

**只留「保真约束」，不留「形式约束」**：层数、怎么分、用什么图，agent 自己定；
但页面上每一行代码、每一个行号、每一句英文引文、每一个提交号，都由 `build.py` 对着仓库核。

证据等级（底稿和画布通用）：【注释】【提交】【文档】【测试】= 有出处；【推断】= 研究员自己的推理；
【观点】= 改进意见；另有「没查到为什么」一节，查不到就明说，不硬编。

## 讲解员为什么是「一个团队」

第一次是**单个讲解员**读完整份底稿再做整张画布：跑了约 70 分钟没有交出可用产物，被我叫停。
原因是 137KB 底稿 + 源码 + 自己写的页面，每一轮都要整体重读，越往后越慢。

改成团队：

1. **框架负责人**：只做 DSL / 构建 / 模板 / 截图脚本 / 作者指南，不碰内容。
2. **总架构师**：读底稿的总览部分，定顶层树和槽位（每个槽位 = 一个可以独立写的分支）。
3. **内容作者 ×N（并行）**：每人只读底稿的一段 + 对应源码，写一个 `content_*.py`。
4. **总装 + 独立核验**：主会话做（构建、机械核对、看截图、对着源码抽查）。

如实说明哪些是谁定的：**槽位表和底稿切段边界是我（主会话）定的**；树的形状、中间节点
（`pick` / `pace` / `trig` / `main` / `ret` / `idx`）、每个分支再怎么细分、用流程 / 图 / 逐帧 / 表格哪种形式，
是各 agent 自己定的。也就是说这一版还不是「完全由 agent 决定结构」。

迭代上限（作者定死）：讲解员每人最多 3 轮「截图 → 看 → 改」，保真核对一次，最多问研究员 1 个问题。
实际每个 agent 用了 0–1 轮，没有人向研究员提问。

## 核对了什么 / 没核对什么

机械核对（全量）：
- 构建 0 WARN：锚点行号存在、提交存在、英文引文 `q` 在所指行 / 提交说明里出现、`has` 子串命中。
- `spot_anchors.py`：364 条锚点 bad = 0；957 行代码逐行与仓库一致。
- `shot.js` 9 个节点 × 2 种视口：无横向溢出，控制台 0 错误。

人工对源码（抽查）：
- `evict.c:184–214` 插入逻辑 对 `pool.demo` 全部 9 帧；`evict.c:636–668` 对 `loop.take` 各帧。
- 内容作者自己标了「底稿里没有、我加的」的条目（`who='me'`）：`server.c:4942–4949` 注释、`evict.c:408/419`
  双返回的推断、`db.c:3010–3019` 先量后删与通知顺序、`db.c:3060–3070`、注释 181–183 写 "smaller"
  而代码停在第一个「不更小」处——均成立。

**没有核对的**：
- 138 条批注的中文转述没有逐条读（构建只核引文和锚点，不核转述是否忠实）。
- 逐帧演示只看了 `pool.demo` 第 1、7 步的截图；`loop.take` 的演示没看截图（只对了源码）。
- `pick` 页（架构师说修过手机端坐标，没人复看）、多数桌面页、多数叶子页没看截图。
- 没有对着运行中的 Redis 验证；逐帧演示是照源码分支手推的。
- 仓库原有的回归套件没重跑（这次没改任何工具链文件，只新增本目录）。

## 成本（如实）

| 环节 | 报告的 token | 工具调用 | 耗时 |
|---|---|---|---|
| 研究员 | 129,836 | — | — |
| 单讲解员（失败，叫停） | 未知 | — | 约 70 分钟 |
| 框架负责人 | 109,606 | 45 | 约 22 分钟 |
| 总架构师 | 131,187 | 16 | 约 16.5 分钟 |
| 内容：gate + acct | 133,552 | 10 | 约 5.7 分钟 |
| 内容：pool + loop | 117,244 | 12 | 约 13.7 分钟 |
| 内容：delete（换便宜一档模型） | 100,792 | 9 | 77 秒 |

讲解员团队合计约 **59 万**，我事先给作者的估计是「15–20 万」——**低估了约 3 倍**。主要没算到：
每个 agent 启动就要读指南 + DSL + 底稿切片 + 源码，光起步就是几万；框架本身比预想的重。
这个 token 数是运行环境报给主会话的单一数字，它是否把每一轮重复读缓存的量也累加进去，我不确定。

模型对比（只有一个样本，不严谨）：`delete` 分支用便宜一档的模型写，77 秒交付，页面观感与其它分支
没有可见差距，自己修掉了一处非法取值和一处行号偏一；批注更少（13 条 / 7 个代码块，`acct` 分支是 28 条 / 12 块），
但漏了什么它自己写明了。初步立场：内容作者用便宜一档够用，架构师和框架留给强模型。

## 被否 / 没走通的方案

- **固定图元菜单 + 机械切函数**（`cfg`）：泛化到 C 要手拆长函数；作者否决——这是 workflow。
- **单 agent 无规则对照**（`control-no-rules.html`）：能出一张不错的图，讲的主要是「怎么做」；「为什么」只有零星几句，
  且没有出处（全文没有提交引用，也没有证据等级）。这是拆出研究员的直接原因。
- **单讲解员包办**：见上，上下文太大，跑不完。
- **讲解员直接写 HTML**：没采用。改成写节点树数据、由构建脚本取代码——代码保真靠构造保证，不靠自觉。
- **厚交接（研究员产出结构化 JSON）**：没采用。结构是讲解员的活，研究员只交文字 + 锚点 + 证据等级。

## 已知问题

- 截图环境的中文字体没有粗体字形，`**粗体**` 看不出来。
- 手机上图例面板几乎盖住整页。
- 桌面 1440 宽右侧留白偏多。
- `more` 展开态、图例、断链样式没有人看过截图。
- 最深 7 层（如 `delete.core.measure` 在第 6 层），手机上可能偏深。
- `main`、`pick` 各有 6 个子节点（指南建议 2–5）。
- 底稿里 `cd90389b3` 的提交标题写 "Every 10 keys"，而现在代码是 `% 16`；这个要在 `tick16` 分支里讲清，该分支还没写。
- 「讲解员先优化底稿」这一步没有单独产出（没有一份改写后的底稿），优化是各作者在写分支时顺手做的。
