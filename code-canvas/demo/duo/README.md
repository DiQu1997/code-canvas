# duo 实验：研究员 + 讲解员（Redis 淘汰 v1 / v2 / v3）

> 实验品。**没有并入工具链**（不走 validate / render / serve，不上 hub），没有自动化测试。
> 目的是先看一次「两个 agent 分工」能做出什么效果，再决定往哪优化。

问题：**Redis 内存超过 `maxmemory` 之后怎么腾内存、为什么这么做**（`performEvictions()` 一条线）。
仓库 `redis/redis` @ `fd7710ca2`（源码不入库，构建时要一份 clone）。

## 为什么做这个（方向转折）

前一阶段（`demo/generalize/`、`cfg` 图元）走的是「把程序压成固定 pattern → 固定图元」。作者的判断：
那是 **workflow 不是 agent**——切点、命名、用哪种图，都不该由我们写死。于是拆成两个角色：

| 角色 | 输入 | 输出 | 约束 |
|---|---|---|---|
| 研究员 | 一句问题 + 仓库（可用 git blame / log） | 一份**文字底稿**：怎么做的 + 宏观/微观的「为什么」 | 每个论断带 `文件:行`；每个「为什么」带证据等级 |
| 讲解员 | 底稿 + 仓库 | 一张自顶向下、可递归下钻的画布 | 代码必须是仓库原文；锚点 / 引文 / 提交机械核对 |

**只留「保真约束」，不留「形式约束」**：层数、怎么分、用什么图，agent 自己定；
但页面上每一行代码、每一个行号、每一句英文引文、每一个提交号，都由 `build.py` 对着仓库核。

证据等级（底稿和画布通用）：【注释】【提交】【文档】【测试】= 有出处；【推断】= 研究员自己的推理；
【观点】= 改进意见；另有「没查到为什么」一节，查不到就明说，不硬编。

## 讲解员为什么是「一个团队」

第一次是**单个讲解员**读完整份底稿再做整张画布：跑了约 70 分钟没有交出可用产物，被我叫停。
原因是 137KB 底稿 + 源码 + 自己写的页面，每一轮都要整体重读，越往后越慢。

改成团队：

1. **框架负责人**：只做 DSL / 构建 / 模板 / 截图脚本 / 作者指南，不碰内容。
2. **总架构师**：读底稿的总览部分，定顶层树和槽位（每个槽位 = 一个可以独立写的分支）。
3. **内容作者 ×N（并行）**：每人只读底稿的一段 + 对应源码，写一个 `content_*.py`。
4. **总装 + 独立核验**：主会话做（构建、机械核对、看截图、对着源码抽查）。

如实说明哪些是谁定的：**槽位表和底稿切段边界是我（主会话）定的**；树的形状、中间节点
（`pick` / `pace` / `trig` / `main` / `ret` / `idx`）、每个分支再怎么细分、用流程 / 图 / 逐帧 / 表格哪种形式，
是各 agent 自己定的。也就是说这一版还不是「完全由 agent 决定结构」。

迭代上限（作者定死）：讲解员每人最多 3 轮「截图 → 看 → 改」，保真核对一次，最多问研究员 1 个问题。
实际每个 agent 用了 0–1 轮，没有人向研究员提问。

## v2：同一份内容，换成一张可缩放的画布（只改讲解员的表现层）

作者的要求：讲解员的展示方式要换成更高级的互动，视角上更像早先的 2D 缩放画布，可以用现成的图形 / 可视化库。
只动「怎么呈现」这一个点，研究员和内容都不动。主会话直接做，没有派 agent。

**怎么做的**

- 内容一个字没动：同一批 `content_*.py` → 同一个数据块。保真约束照旧（代码由构建从仓库取，锚点核对同一份 `anchors.json`）。
- 整个页面是一张连续的 2D 画布。每个节点是一块「框」；它的子节点不是链接，而是**那一页本身的缩小活副本**，
  嵌在父页面的小块里（CSS `transform: scale`，下半截裁掉）。放大一个小块，看到的就是那一页，不换页、不重排。
- 镜头用 D3（`d3-zoom`）：点任意一块 → `d3.interpolateZoom` 飞进去；拉远 → 当前页自动退回上层。
  「当前在哪一页」由视口中心落在哪个框上判定（带迟滞）；地址栏 `#/节点id`、面包屑、侧边地图、上一页 / 下一页都只是移动镜头。
- 远近分级显示：屏幕上缩到 25% 以下的块只显示一个大标题，3.5% 以下只剩色块。所以拉远是模块地图，拉近是真实代码。
- 逐帧演示变成真动画（格子位移，浏览器自带的 WAAPI），可以自动播放。
- 手机：单指拖动（带轴锁定和惯性）、双指缩放、底部停靠条（上层 / 上页 / 下页 / 下层）、图例是底部抽屉。
  桌面：滚轮 = 平移，Ctrl / ⌘ + 滚轮 = 缩放；宽屏时子块排在右侧一列。

**选库的立场**

- **D3 当镜头 + DOM / SVG 放内容**，不用 Konva / PixiJS / Two.js。这张画布九成是文字和代码；位图画布要自己排文字，
  放大会糊，不能选中 / 搜索 / 复制，读屏也废了。Chart.js / ECharts 是统计图库，这里没有统计图。
- Konva 的位置：以后要做「人在画布上拖、圈、批注」时，作为叠加层再加，不当底座。
- D3 整包内联（约 273 KB），页面仍然自包含、离线可用。实际只用到 zoom / selection / transition / interpolate / timer，
  单独打包约 60 KB，但要引入打包器，这次没做。v2 页面 525 KB，v1 是 230 KB。

**被否的做法**（多数是设计时否掉的，没有都实现出来对比）

- 所有节点按真实大小铺成一张大图、整体等比缩放：54 个节点铺开后，全景里每块都小到看不清，手机上更糟。
- 固定比例的分形排布（每一层固定缩成一条）：最深 7 层时底层缩到看不见，各页长短差很多，留白失控。
- 小块里把整页完整塞进去（contain）：长页被压成细长条；改成「按宽度缩 + 裁掉下半截」。
- 扁平 DOM（所有框平铺，用绝对坐标摆）：页面里任何一处展开代码都要全盘重算；改成真嵌套，让浏览器自己排。
- 不量 DOM、用公式推每个框的位置：字体和换行一有差别就飞不准；改成飞之前实测，落地后再量一次校正。
- 桌面两列缩略：小块太窄，缩略内容不可读；改成右侧单列。
- `will-change` 提前合成层：没加，担心放大时文字发糊（没有实测对比）。
- 没做的：小地图、节点间连线、搜索、可交互的模拟器、拖出边界的限制。

**核对了什么**

- `shot_zoom.js`：桌面 1440×900 共 20 项、手机 390×844 共 15 项，**35 项全过**，控制台 0 错误（1 倍和 2 倍各跑过）。
  桌面：点块飞入并贴顶对齐、深链、批注深链只闪一条且在自己那页、滚轮只平移、Ctrl + 滚轮缩放、拉远退回上层、
  远景标签出现、方向键、锚点就地展开、地图 / 图例、空白处拖动、逐帧点步和自动播放。
  手机：单指只走一个方向、松手有惯性、双指捏合、点块飞入、底部按钮、逐帧点到第 5 步、地图跳转。
- 截图自检 2 轮（上限 3 轮）。
- `spot_anchors.py`：364 条锚点 bad = 0，957 行代码逐行一致（数据与 v1 是同一份）。

**过程中出的错（如实）**

- 第 1 轮检查 33 / 35：两项失败是**检查脚本的错**（等待函数在飞行中途就取样），页面本身落点是准的；改了脚本。
- 第 1 轮截图发现**页面的错**：手机上示意图最右一个可点的框被裁掉一条边。原因是一条通用样式（流程步里「下钻 ›」用的 `.go`）
  同时命中了示意图里可点的框，把它们右移了 8px。**v1 模板有同样的问题**，一并修了，`redis-eviction-v1.html` 重新生成过
  （与上一次提交只差这一条样式）。
- 2 倍截图时「滚轮平移 300px」一项不过：2 倍模拟下合成滚轮事件的增量被减半，空白页也能复现，判断是模拟环境的问题；
  检查改成对「页面实际收到的滚轮量」比。**真机高分屏上的滚轮速度没法在这里验证。**

**没有核对的 / 已知取舍**

- 只在无头 Chromium 里跑过。**iOS Safari 没测**——手势手感、放大后文字清晰度、嵌套缩放的性能都可能不一样。
- 每个子节点都是活副本，同一页在各级祖先里各有一份，DOM 比 v1 大得多；低端手机的流畅度没测。
- 手机上读长文，拖画布不如 v1 的原生滚动舒服，所以 v1 留着，两个页面并存。
- 手机上的「全景」只是回到根页面，没有真正的鸟瞰（屏幕太窄，缩到全貌就看不清）。
- 鼠标在当前卡片上拖动是选中文字，不是平移；平移要拖空白处或用滚轮。
- 深层节点背后能看到淡掉的上层页面（遮罩 86%，手机 93%），是「你在里面」的提示，也可能有人嫌杂。
- 拉远时叶子页的小块仍显示缩略、旁边的块已变成大标题（两者缩放比不同），不一致，没处理。
- 悬浮的底部停靠条会盖住页面最下面一行，要再拖一下才露出来。

**成本**

- 事先估计 $15–30。计费表读数从 $221.95 到 $226.23（+$4.3），但这一整段是在同一个还没结束的回合里做的，

## v3：顶层换成一张「机器图」，讲解钉在图上（内容是讲解员 agent 写的）

**起因。** 作者看了 v2 之后说：喜欢 `sglang-radix-v5` 最上层那种「机器图」式的可视化，但「总觉得好像还是不够能理解」；
v2 的讲解和分类也喜欢，想两样结合。定下来的方向：**顶层用机器图，把讲解拆成小块钉在图上对应的位置，分类变成图层开关**。
作者又加了一条：不要只在图上写一两句话——**每一条线、每一个模块都能展开一张说明**，从高层讲清
「这里是干什么的 / 怎么设计的 / 为什么这么设计、有什么好处」。这一版只做最上面这一屏，下面各层仍是 v2 的页面。

**分工（作者纠正过一次）。** 我一开始打算自己把 Redis 的内容手写进去，作者叫停：「为什么不开 agent，我们的核心是设计出一个
agent」。于是改成：

## 被否 / 没走通的方案

- **固定图元菜单 + 机械切函数**（`cfg`）：泛化到 C 要手拆长函数；作者否决——这是 workflow。
- **单 agent 无规则对照**（`control-no-rules.html`）：能出一张不错的图，讲的主要是「怎么做」；「为什么」只有零星几句，
  且没有出处（全文没有提交引用，也没有证据等级）。这是拆出研究员的直接原因。
- **单讲解员包办**：见上，上下文太大，跑不完。
- **讲解员直接写 HTML**：没采用。改成写节点树数据、由构建脚本取代码——代码保真靠构造保证，不靠自觉。
- **厚交接（研究员产出结构化 JSON）**：没采用。结构是讲解员的活，研究员只交文字 + 锚点 + 证据等级。
